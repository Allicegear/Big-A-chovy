# daily-stock-analysis 重构执行说明

> 交给执行 agent 的任务说明。目标是修复已经核实的筛选结果与运行状态问题，再收敛 CLI 和看板两套重复流水线。本文不是交易规则；规则以根目录 `选股框架.md` 为准。

## 任务目标与完成定义

在保留现有 CLI、GUI、实时看板及报告字段兼容性的前提下，让同一份行情、配置、公告结果和历史状态，在 CLI 与看板得到相同的基础候选、风险标签、资金排名及状态转移。看板专有的缓存、分钟量能和展示信息可以继续作为附加字段。

完成时必须同时满足：

1. `top` 只影响展示行数，不影响完整候选集合、双池交集、准交集、状态推进及公告核验范围。
2. 公告 `avoid`、`unknown` 不进入正式可买资格；`watch_risk` 按框架减分或标注，不因“非 clean”被当成一票否决。检查所有池子和两个状态机，不能只改一处 `if`。
3. 看板与 CLI 均执行观察池突破状态机；同一输入的资金排名、`sector_boost`、公告门禁及状态结果一致。
4. 看板宣布一轮超时或失败之后，该轮不能继续覆盖持久状态；后一轮也不能与旧轮并发读改写同一状态。失败时最近有效报告的保留行为继续有效。
5. 自动化验证不读写真实运行状态和报告目录；用户已有的状态、持仓、决策记录、影子库及未提交改动保持原样。
6. 筛选工具仍只做发现和证据输出，不生成真实仓买卖裁决，不自动下单。

## 开工前必须读与禁止事项

- 先读根目录 `AGENTS.md`、`选股框架.md`、`CLAUDE.md`、本目录 `SKILL.md` 和 `README.md`。本次不做买卖裁决，但修改筛选门禁须逐条对照框架。
- 当前工作区已有大量未提交改动，涉及目标文件和新增测试。先记录 `git status --short` 与目标文件 diff；在现有内容上继续，不执行 reset、checkout、覆盖式复制或清理用户文件。
- 不运行 `tools/shadow_tracker.py` 的扫描模式（无参数或 `--date`）；`--report` 才是允许的只读用法。
- 任何手动引擎、看板或范围验证，必须在**启动进程前**设置 `A_SHARE_STATE_DIR` 和 `A_SHARE_REPORT_DIR` 为独立临时目录。行情日期隔离不能代替目录隔离。测试套件也不得写真实状态。
- `筛选结果/`、`决策记录/`、`holdings.json`、交易金额及影子样本库不得提交或传到外部服务。不要把这些数据复制进测试夹具、日志或任务报告。
- 不改动交易规则权威值，也不把实验信号升级为真实仓许可；如果实现与框架冲突，按框架修实现并在交付记录中列出行为变化。

## 推荐实施顺序

### 0. 建立可复现的安全验证环境

1. 列出 CLI、`realtime_engine`、`realtime_dashboard`、`web_workbench` 对行情、公告、配置、状态、报告的读写点，标明哪些发生在计算阶段，哪些发生在最终落盘阶段。
2. 为测试创建独立状态目录与报告目录，先确认导入和测试不会写入脚本目录中的真实 `flow_snapshot.json`、`intersection_state.json`、`watchlist_breakout_state.json`、`.kline_cache.json` 等。
3. 修正 `test_runtime_state_isolation.py:test_default_matches_historical_location` 的测试方式：它目前假定测试进程没有设置隔离环境变量，因此放在隔离套件里会失败。可用只检查路径、不落盘的独立子进程验证默认行为；其余测试始终在隔离目录运行。
4. 造**合成**固定输入夹具，覆盖完整行情、公告失败、备用行情、跨日状态、三种交易板、`top` 变化、超时。不要使用私有报告或持仓内容。保留修改前的输出合同与差异清单。

### 1. 先补失败用例，再修规则结果

1. 给内部候选与展示候选明确不同变量。严格超短、趋势观察、趋势确认、低吸及观察池的内部集合在排序后保留完整，状态机、交集、公告查询与候选计数读取内部集合；渲染或对外展示时才按 `top` 截取。公告查询范围按**完整候选集合**确定，不能由 `top` 决定；不要把仅供解释的全部诊断近似命中行加入请求范围。测量请求量，必要时复用已有缓存或批量查询，不通过截断资格集合控制成本。
2. 把公告状态处理集中成一份政策函数或表：`clean` 正常；`watch_risk` 保留软风险与减分语义，不得自行发明框架未给出的数值罚分；`avoid` 与 `unknown` 阻断正式资格。检查 `apply_announcement_pool_gates`、交集状态机、准交集拒绝原因、观察池突破、资金排名和输出标签，不得只改 `_entry_allowed`。保留框架明确要求 `clean` 的**特定实验加分条件**（如 `sector_boost`）；这种加分未获得，与整只股票被一票否决是两回事。实验状态仍不得因此获得真实仓权限。
3. 对 `watchlist` 的 `unknown` 使用框架的一票否决语义。可继续展示“数据不足”观察信息，但不得输出 `CONFIRMED/B_BREAKOUT/A_STRICT` 等看似升级的状态。
4. 资金优选统一在公告结果可用、`Enriched.risk_status` 已同步后执行；传入同一份 `flow_history`。公告失败采用 `unknown`，不能用先算出的分数或标签绕过门禁。

### 2. 收敛 CLI 和看板的核心流水线

1. 从两份入口中提取**一次**共享的筛选流程，优先复用现有纯计算函数；不要为拆文件而重写全部 5500 行。推荐把阶段固定为：行情与质量判定 → 丰富数据 → 资金基准/否决 → 完整候选池 → 公告核验及风险映射 → 资金排名 → 观察池突破 → 双池交集/准交集 → 交集状态机 → 展示裁剪与附加字段。
2. CLI 和看板调用同一个核心入口。网络模式、K 线缓存、进度回调、分钟 K 扩展可作为显式参数或注入的依赖；不能靠看板导入时 monkey-patch `screen.fetch_kline` 来改变所有调用点的含义。若暂时保留 monkey-patch，必须在文档中列出其生命周期与并发边界，并有回归测试。
3. 核心结果建立稳定字段合同，至少涵盖 `meta` 的行情日期/源/完整性、所选交易板、各候选池、公告风险映射、两类状态、资金优选、错误及警告。看板特有的分钟量能/温度计是附加字段；CLI 的 Markdown 和 JSON 只负责渲染同一核心结果。
4. 保留旧快照读取与兼容标签，避免重构导致历史看板无法打开。报告表格若需解析，按表头动态定位，不硬编码列号。

### 3. 处理超时与状态提交

1. 为每轮引入唯一轮次标识和明确的生命周期（进行中、完成、超时、失败、已提交）。网络/计算可超时，但超时轮不能再提交运行状态或报告。
2. 将资金基准、交集状态、观察池突破状态、K 线缓存等写入动作盘点后，保证只有成功且仍有效的轮次可提交。实现可选择可终止的独立进程，或“计算出状态增量后由调度器唯一提交”的方案；无论采用哪种，必须证明旧工作线程无法在超时后写正式状态，也无法与下一轮交叉覆盖。
3. 对关键状态文件采用临时文件加 `os.replace` 的原子写入；保留现有 JSON schema 与读取兼容。失败要记录可诊断错误，不能被 `except Exception: pass` 吞掉并伪装成正常空状态。
4. 只在行情数据日期匹配且轮次有效时推进确认次数。相同快照重跑不得重复确认；跨交易日须按既有规则清理或继承相应状态。失败或降级快照不得清空上一份有效状态。

### 4. 安全和结构清理

1. 在隔离环境逐个验证行情端点的证书链及本机代理行为，移除不必要的 `verify=False` / `_create_unverified_context`。确有代理自签 CA 需求时使用可配置 CA bundle；不要把证书失败转换为“无候选”。
2. 将剩余职责按行情适配、规则计算、状态存储、报告渲染、HTTP 服务拆分；保留薄兼容层以维持 CLI、GUI 和现有测试导入路径。只拆对当前风险有帮助的模块，避免无关格式化和大规模重命名。
3. 清点静默吞错；对关键状态/公告/行情错误至少输出结构化警告或失败状态。非关键 UI 兼容异常可保留降级处理。

## 验收用例与交付物

### 必须自动验证

- `top=3/15/50` 使用相同合成行情时，内部候选代码集合、交集、状态增量、公告核验代码集合一致；可见表格行数按 `top` 变化。
- `clean/watch_risk/avoid/unknown` × 交集、准交集、低吸、资金优选、观察池突破形成风险矩阵；超大单为负继续一票否决。
- 同一固定输入同时走 CLI 与看板入口，对关键字段做结构化对比，并解释允许的看板附加字段。至少覆盖 clean 的 `sector_boost`、`coalition` 历史条件、公告失败、备用行情及所选交易板变更。
- 超时、失败和重试的并发测试：旧轮完成时不能晚写或覆盖新轮；状态 JSON 始终可解析；最近有效快照按既有行为保留。
- 状态日期与快照 ID 测试：同快照不重复确认，跨日按规则重置/继承，降级输入不清空有效状态。
- 现有相关单元测试与完整测试套件在隔离环境通过。若既有测试断言与权威框架冲突，更新测试并注明原因；不能为过测试保留错误规则。

### 验收时人工核对

- CLI JSON/Markdown、看板 `/api/data`、工作台报告可以正常展示；候选字段、风险说明、交易板标签与权限提示未丢失。
- 记录重构前后合成输入的差异。预期差异只包括本说明 R1–R5 明确修正的行为，以及必要的错误提示；其余候选排序/分数/状态变化必须解释和修复。
- 记录网络请求数、单轮耗时和报告大小的前后对比，避免“完整候选”导致明显请求爆炸或刷新周期无法完成。
- 检查 `git status --short --ignored`，确认未跟踪或暂存私有报告、决策记录、持仓及影子库，且真实运行状态文件没有因测试改变。

### 交付给主 agent 的内容

1. 修改文件清单及每项原因，特别列出与《选股框架.md》对齐的行为变化。
2. 测试命令、通过数、隔离目录设置、未通过项与原因。
3. CLI/看板对照结果、超时并发验证结果和性能前后对比。
4. 尚存风险、需要后续单独处理的事项；不把未完成事项表述为已修复。

## 执行时的决策原则

优先交付可验证的行为修复，再做结构调整。每完成一阶段就运行对应合成回归；若发现新规则冲突，先定位《选股框架.md》的权威条款。不要用历史私有报告“调”出看似正确的结果，也不要用仅检查源码字符串存在与否的测试替代行为测试。
