## 必须修复的问题

### 1. [P1] 公告业务失败被解释为“无公告”，继而放行为 clean

位置：`daily-stock-analysis/scripts/a_share_daily_screen.py:1185–1204`。

合成主源返回 `{"success": false, "code": 429, "data": null}`。当前仅因存在 `data` 字段即接受响应，得到 `titles=[]`，最终分类为 `clean`，**没有调用巨潮备用源**。

这违反公告失败/unknown 一票否决，也违反方案中“失败不能伪装正常空结果”的验收条件。修复应校验业务成功标记、列表结构和数量/分页信息；主源失败切备源，两源均失败保持 unknown 或保留有效的既有 avoid。备用源同样需要区分合法空列表与失败/null，沿用项目唯一风险分类规则。

复验：业务失败但 HTTP 200、空对象、`data:null`、合法零条、主源失败备源成功、双源失败、旧缓存 avoid 均需覆盖，确认各池及状态机不会因异常降级而放行。

### 2. [P1] 财务实绩判定会取错字段，并把冲突指标或旧年度数据判为盈利

位置：`tools/query_financials.py:88–136`、`:212–225`。

已复现三种输入：

| 输入 | 实际输出 | 问题 |
| --- | --- | --- |
| 2026-06-30，EPS=-0.2，归母净利润=100 | `profit` | 任一指标正值优先于负值，冲突被忽略 |
| 2025-12-31，EPS=1，归母净利润=100 | `profit` | 没有核验本年实绩 |
| 同比字段先出现，值120；实际归母净利润=-100；EPS缺失 | 净利润120，`profit` | 子串字段匹配把同比增长率当净利润 |

输出还把亏损描述成“不宜重仓”，把部分盈利数据描述成“安全”，与方案要求的核验语义不符。

修复应优先精确字段匹配，分离实绩、同比、动态PE、TTM、快照和预告；明确报告期及公布时间；冲突或缺少本年证据不得标成安全盈利。真实仓门禁仍由框架裁决，工具不另立 PE 或仓位规则。另需核实腾讯备用快照是否实际提供动态PE/TTM/PB，避免宣称已补全而返回缺失值。

### 3. [P1] 分笔窗口不足被标为充分，收盘成交额校验因时间格式不一致失效

位置：`tools/data_sources/tencent.py:152`、`:263–291`。

- 两笔交易分别在10:00和10:01，请求15分钟窗口：实际 `coverage_minutes=1.0`，但 `data_sufficient=true`，买卖比10被作为充分窗口结果返回。
- 收盘快照时间 `153000`，快照成交额1000，分笔金额合计200：实际 `status=ok`、`warnings=[]`。时间比较使用 `HHMMSS >= "15:01:00"`，校验分支没有执行。

修复应统一时点格式，按所选窗口判断覆盖，缺失时明确不足；成交额完整性校验需采用同一交易时段口径，并影响可信状态。完整序列检查还需覆盖开头缺页、原始顺序倒退、重复、跨日和快照期间新增成交，不能仅在排序去重后的数据上检查。

### 4. [P1] 交易日历一次故障会被全天缓存，网络恢复后不再确认交易日

位置：`daily-stock-analysis/scripts/realtime_dashboard.py:263–303`。

合成场景：工作日首次官方日历和指数备源均不可用，下一次官方源已恢复。实际官方查询仅调用一次，缓存仍为 `unavailable`，`_trading_day_pending=true`。当天自动筛选会一直保持未确认状态。

修复应给未确认/失败结果设置有限重试间隔和冷却，恢复后重新确认；已确认假期保持正确缓存。不能用简单工作日判断替代官方/指数确认。

### 5. [P2] 增减持和回购报表名称不正确，相关事件能力实际不可用

位置：`tools/data_sources/events.py:34`、`:52`、`:163–177`。

公开源限量冒烟：

| 报表 | 实际返回 |
| --- | --- |
| `RPT_HOLDER_INCREASE_DECREASE`（当前增减持配置） | `code=9501`，报表配置不存在 |
| `RPT_SHARE_HOLDER_REPURCHASE`（当前回购配置） | `code=9501`，报表配置不存在 |
| `RPT_SHARE_HOLDER_INCREASE` | `success=true`，count=13 |
| `RPTA_WEB_GETHGLIST_NEW` 配 `SECURITY_CODE` 过滤 | `SECURITY_CODE列不存在` |

最后一项只证明不能复用统一证券字段，并未验证回购修正后可用。应逐类核对上游报表、证券字段、日期字段、金额/比例单位、分页及实际响应，再记录实测结果。

此外，当前只有同时提供 start/end 才生成日期过滤，而非解禁类型传入 end=None，历史 `as_of` 并未约束事件。解禁需区分公告日期与实际解禁日期，不得以最近公告筛选代替未来解禁覆盖。

### 6. [P2] 缓存会丢失故障状态和跨实例更新

位置：`tools/data_sources/sentiment.py:189–193`、`events.py:203–206`、`cache.py:36–41`、`:55–116`。

- 合成情绪场景：涨停池成功，炸板/跌停池失败；首次 `partial`，再次命中缓存变为 `ok`，warnings消失，但内部两个池仍 unavailable。事件缓存存在同类状态重建问题。
- 两个 `JsonCache` 实例先加载同一空文件，再分别写 key a/b，实际持久化仅剩 b。实例级锁和原子替换并不能保护整个“读取—修改—写入”过程。相同进程的临时文件名还会冲突。

修复应缓存完整契约状态/错误/时点，而非命中时推断正常；使用共享锁和可靠的跨进程读改写保护，或采用适合并发的数据存储，并测试多实例、多线程、多进程、旧缓存与失败冷却。

### 7. [P2] 题材板块被证券代码过滤丢弃，历史龙虎榜会混入所选日期之后的数据

位置：`tools/data_sources/context.py:138–146`、`:330–350`。

合成题材响应包含 `f12=BK1001/BK1002` 时，实际结果为 `[]`。板块标识被当成股票证券代码比较。修复应按源结构分离股票身份与板块身份，并实测请求路由。

龙虎榜静态审查发现仅按股票代码过滤，没有 `TRADE_DATE <= as_of`；买卖席位也未限制到对应上榜记录的交易日期。返回却将请求日期标为 data_date。修复后需验证历史截止、同日/多日榜单及席位归属/去重；不支持历史时点的 topic 应明确说明限制，不能把最新数据标为旧日证据。

### 8. [P2] 背景查询仍同步占用筛选锁，失败时可能延迟结果和下一轮

位置：`daily-stock-analysis/scripts/realtime_dashboard.py:402–405`、`:507–516`；`tools/data_sources/background.py`。

静态审查发现市场背景在核心引擎完成后同步请求官方日历及三个情绪池，此时仍持有 `_screening_lock`，且不受前面引擎等待期限覆盖。有限的逐请求重试不等于完整轮次预算。方案明确要求附加证据不能阻塞下一轮筛选。

应采用共享低频缓存/异步刷新和总时限，已有核心结果及时发布；外部源失败有冷却，不每轮重新发起整组重试。新增 HTTP 默认路径也需接入项目的网络择优与 TLS 配置，而非建立与既有路径独立的默认 urllib 链。补充失败耗时、并发请求合并、冷/热请求数及CLI/自动看板/手动工作台一致性验证。

### 9. [P2] 工作台交付仍缺少方案要求的可读详情和独立加载行为

位置：`daily-stock-analysis/scripts/workbench_static/app.js:243–309`。

当前主要以折叠 JSON 展示证据，且等待 `Promise.all` 全部完成才一次性显示；没有按topic即时更新成功/失败卡片。财务接口未传查询日期，分笔接口也没有历史查询能力，但统一日期输入没有说明这些限制。商品查询默认所有股票均查铜，未完成板块/合约映射。异常波动/监管监控虽然有后端topic，仍缺少对应的核验入口。

需对照方案补齐候选详情、分笔与五档组合核验、关键财务/事件字段的可读摘要、独立加载、日期适用范围、商品映射和核心topic入口；再进行窄屏、主题、键盘与可访问性复验。原始JSON可作为补充证据。
